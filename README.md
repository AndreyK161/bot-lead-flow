# bot-lead-flow

Небольшой сервис: принимает событие о новом лиде из Bitrix24 и шлёт красивое
уведомление в Telegram. Поддерживает назначение менеджера, перенос в мусор
и ручное создание лидов через второй бот.

## Как это работает

1. В Bitrix24 создаётся **исходящий вебхук** на событие `ONCRMLEADADD`.
   При создании лида Bitrix сам делает POST на `/bitrix/webhook` этого сервиса
   (form-urlencoded), передавая `event`, `data[FIELDS][ID]` и
   `auth[application_token]`.
2. Сервис сверяет `application_token` с `BITRIX_APPLICATION_TOKEN` из `.env` —
   если не совпадает, отвечает 403.
3. По `ID` лида сервис дозапрашивает полные данные через **входящий вебхук**
   методом `crm.lead.get`, резолвит источник (`crm.status.list`) и
   ответственного (`user.get`).
4. Собирает HTML-сообщение и отправляет его в Telegram через
   `sendMessage` (`parse_mode=HTML`).

## Установка

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

Заполните `.env` (см. разделы ниже, как получить каждое значение).

Запуск локально:

```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

Эндпоинт: `POST /bitrix/webhook`. Для продакшена сервису нужен публичный
HTTPS-адрес (Bitrix24 стучится извне) — например, через reverse proxy /
хостинг с доменом, или туннель (ngrok/Cloudflare Tunnel) для теста.

## Настройка Bitrix24

### 1. Входящий вебхук (для чтения данных лида)

1. Откройте портал → **Приложения → Разработчикам → Другое → Входящий вебхук**.
2. Добавьте вебхук, выберите права (scope): **crm**, **user**.
3. Скопируйте полученный URL вида
   `https://your-portal.bitrix24.ru/rest/1/xxxxxxxxxxxxxxxx/`
   в `BITRIX_WEBHOOK_URL`.

### 2. Исходящий вебхук (уведомление о новом лиде)

1. Там же: **Приложения → Разработчикам → Другое → Исходящий вебхук**.
2. Событие: `OnCrmLeadAdd`.
3. Обработчик (URL): публичный адрес вашего сервиса, например
   `https://your-domain.example.com/bitrix/webhook`.
4. Bitrix сгенерирует токен приложения (application token) — скопируйте его в
   `BITRIX_APPLICATION_TOKEN`. Именно это значение сервис сверяет в каждом
   входящем запросе, чтобы отбрасывать чужие POST-запросы.
5. Сохраните и создайте тестовый лид — в логах сервиса и в Telegram должно
   появиться уведомление.

## Настройка Telegram-бота

1. Откройте [@BotFather](https://t.me/BotFather), отправьте `/newbot`,
   следуйте инструкциям, получите токен вида `123456789:AA...` —
   это `TELEGRAM_BOT_TOKEN`.
2. Добавьте бота в нужный чат/группу (или используйте личный чат с ботом).
3. Узнайте `chat_id`:
   - для группы: добавьте бота, отправьте любое сообщение в группу, затем
     откройте `https://api.telegram.org/bot<TOKEN>/getUpdates` и найдите
     `"chat":{"id": -100...}` в ответе;
   - либо воспользуйтесь ботами вида `@getmyid_bot` / `@userinfobot`.
4. Значение (обычно отрицательное число для групп) впишите в
   `TELEGRAM_CHAT_ID`.


## Обработка edge-кейсов

- Пустые/отсутствующие `PHONE`/`EMAIL` (multifield) — строки просто
  пропускаются в сообщении.
- Отсутствующий `SOURCE_ID` или `ASSIGNED_BY_ID` — соответствующие строки не
  добавляются, доп. запросы к Bitrix не делаются.
- Все пользовательские текстовые поля (имя, `SOURCE_DESCRIPTION`, комментарий)
  экранируются через `html.escape` перед вставкой в HTML-сообщение — чтобы
  случайные `<`, `>`, `&` в данных лида не ломали разметку Telegram.
- Ошибки Bitrix API (`{"error": ...}` в теле ответа 200 OK) и ошибки Telegram
  API логируются и возвращаются как 502, чтобы это было видно в логах.

## Бот ручного ввода

`TELEGRAM_CHAT_ID` — основной получатель уведомлений. Дополнительные личные
чаты или группы указываются в `TELEGRAM_NOTIFICATION_CHAT_IDS` через запятую.
Каждый получатель в личном чате должен сначала нажать `/start` в основном
боте. `ADMIN_TELEGRAM_USER_IDS` определяет права на кнопки, а не подписку
на уведомления. Для ручных заявок доставка каждому получателю сохраняется
отдельно: при ошибке повторяется только доставка в отсутствующие чаты.

Второй бот доступен администраторам из `ADMIN_TELEGRAM_USER_IDS` в личных
сообщениях. Отправьте один телефон, username или ссылку на профиль. Бот
покажет контакт и источники. Выбор источника создаёт лид в CRM и карточку
в основном боте. Назначение менеджера через основной бот обновляет карточку
в боте ввода. Кнопка «В мусор» после подтверждения переносит лид на стадию
«Мусор» и обновляет обе карточки. Лид остаётся в CRM, ссылка сохраняется.
Стадия определяется по названию «Мусор» в справочнике CRM. Перед показом
успеха сервис повторно читает лид и проверяет его `STATUS_ID`.
До выбора источника доступна отмена.

Команды: `/sources` — включить/выключить источники кнопками;
`/cancel` — отменить все ещё не переданные заявки; `/help` — инструкция.
Справочник загружается из CRM с реальными `STATUS_ID`. Изначально включены
TikTok, Instagram, WhatsApp, Telegram (включая Tgapi), ВКонтакте,
Одноклассники, YouTube и MAX. Изменения списка сохраняются при обновлении
справочника; чтобы добавить новый источник, сначала создайте его в CRM,
затем откройте `/sources` и включите его.

Настройки: `MANUAL_BOT_TOKEN`, отдельный `MANUAL_WEBHOOK_SECRET`,
`DATABASE_PATH`. Зарегистрируйте Telegram webhook второго бота на
`https://<домен>/telegram/webhook/manual` с `secret_token`, совпадающим с
`MANUAL_WEBHOOK_SECRET`, и `allowed_updates=["message","callback_query"]`.
Текущий nginx location `/telegram/webhook` также пропускает этот маршрут.

SQLite хранится в `./data`, примонтированном в Docker; каталог нужно
включать в резервные копии. Запускайте один процесс uvicorn: блокировки
операций рассчитаны на один экземпляр сервиса. Фоновое восстановление
каждые 15 секунд повторяет отправку/обновление карточек после API ошибок.
Если создание CRM лида прервалось с сетевой ошибкой, сервис ищет его по
уникальной метке, вместо повторного создания. Если CRM не создала лид,
карточка остаётся в статусе проверки: администратору нужно проверить CRM
перед отправкой новой заявки. При разрыве соединения после успешной
отправки Telegram, но до сохранения ID сообщения возможна повторная
карточка; сам лид при повторном webhook не создаётся заново.
