# bot-lead-flow

Сервис отслеживает лиды и сделки из Bitrix24 и отправляет уведомления в
Telegram. Поддерживает назначение менеджера, перенос в мусор и ручное
создание лидов в основном боте.

## Сделки из канбана продаж

Новые сделки из воронки `TRACK_DEAL_CATEGORY_ID` отслеживаются каждые
`DEAL_POLL_INTERVAL_SECONDS` секунд. На портале PravBuro значение `0`
соответствует воронке «Продажа». При первом запуске сервис запоминает
последнюю существующую сделку и не рассылает старые карточки.

Для новой сделки сервис получает связанный контакт, источник и ответственного,
после чего отправляет карточку всем получателям основного бота. Кнопки карточки
позволяют назначить сотрудника отдела продаж и перенести сделку на стадию
«Мусор». Стадия определяется внутри нужной воронки и проверяется после записи.
Доставка и курсор опроса хранятся в SQLite, поэтому перезапуск не создаёт
повторных уведомлений. Также поддерживается событие `ONCRMDEALADD` на уже
существующем `/bitrix/webhook`, если его позднее добавить в исходящий webhook.

Каждый лид, увиденный ботом, сохраняется локально вместе с нормализованными
телефонами. Если у новой сделки заполнен `LEAD_ID`, карточка содержит точную
ссылку на исходный лид и отмечает, видел ли его бот раньше. При копировании
сделки между воронками Битрикс иногда теряет `LEAD_ID`; тогда применяется
резервное сопоставление по телефону связанного контакта. Такое совпадение явно
помечается как совпадение контакта, а не как точная техническая связь.

## Как это работает

1. В Bitrix24 создаются **исходящие вебхуки** на события `ONCRMLEADADD`,
   `ONCRMLEADUPDATE`, `ONCRMDEALADD` и `ONCRMDEALUPDATE`.
   При создании лида Bitrix сам делает POST на `/bitrix/webhook` этого сервиса
   (form-urlencoded), передавая `event`, `data[FIELDS][ID]` и
   `auth[application_token]`.
2. Сервис сверяет `application_token` с `BITRIX_APPLICATION_TOKEN` из `.env` —
   если не совпадает, отвечает 403.
3. По `ID` лида сервис дозапрашивает полные данные через **входящий вебхук**
   методом `crm.lead.get`, резолвит источник (`crm.status.list`) и
   ответственного (`user.get`).
4. Собирает HTML-сообщение и отправляет его в Telegram через
   `sendMessage` (`parse_mode=HTML`).

## Установка

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements.txt
cp .env.example .env
```

Заполните `.env` (см. разделы ниже, как получить каждое значение).

Запуск локально:

```bash
uvicorn app.main:app --host 0.0.0.0 --port 8000
```

Эндпоинт: `POST /bitrix/webhook`. Для продакшена сервису нужен публичный
HTTPS-адрес (Bitrix24 стучится извне) — например, через reverse proxy /
хостинг с доменом, или туннель (ngrok/Cloudflare Tunnel) для теста.

## Настройка Bitrix24

### 1. Входящий вебхук (для чтения данных лида)

1. Откройте портал → **Приложения → Разработчикам → Другое → Входящий вебхук**.
2. Добавьте вебхук, выберите права (scope): **crm**, **user**.
3. Скопируйте полученный URL вида
   `https://your-portal.bitrix24.ru/rest/1/xxxxxxxxxxxxxxxx/`
   в `BITRIX_WEBHOOK_URL`.

### 2. Исходящий вебхук (уведомление о новом лиде)

1. Там же: **Приложения → Разработчикам → Другое → Исходящий вебхук**.
2. Создайте обработчики для событий `OnCrmLeadAdd`, `OnCrmLeadUpdate`,
   `OnCrmDealAdd` и `OnCrmDealUpdate` с одинаковым URL обработчика.
3. Обработчик (URL): публичный адрес вашего сервиса, например
   `https://your-domain.example.com/bitrix/webhook`.
4. Bitrix сгенерирует application token. Скопируйте его в
   `BITRIX_APPLICATION_TOKEN`. Если токены обработчиков различаются, перечислите
   их через запятую. Сервис сверяет токен каждого входящего запроса.
5. Сохраните и создайте тестовый лид — в логах сервиса и в Telegram должно
   появиться уведомление.

## Настройка Telegram-бота

1. Откройте [@BotFather](https://t.me/BotFather), отправьте `/newbot`,
   следуйте инструкциям, получите токен вида `123456789:AA...` —
   это `TELEGRAM_BOT_TOKEN`.
2. Добавьте бота в нужный чат/группу (или используйте личный чат с ботом).
3. Узнайте `chat_id`:
   - для группы: добавьте бота, отправьте любое сообщение в группу, затем
     откройте `https://api.telegram.org/bot<TOKEN>/getUpdates` и найдите
     `"chat":{"id": -100...}` в ответе;
   - либо воспользуйтесь ботами вида `@getmyid_bot` / `@userinfobot`.
4. Значение (обычно отрицательное число для групп) впишите в
   `TELEGRAM_CHAT_ID`.

## Обработка edge-кейсов

- Пустые/отсутствующие `PHONE`/`EMAIL` (multifield) — строки просто
  пропускаются в сообщении.
- Отсутствующий `SOURCE_ID` или `ASSIGNED_BY_ID` — соответствующие строки не
  добавляются, доп. запросы к Bitrix не делаются.
- Все пользовательские текстовые поля (имя, `SOURCE_DESCRIPTION`, комментарий)
  экранируются через `html.escape` перед вставкой в HTML-сообщение — чтобы
  случайные `<`, `>`, `&` в данных лида не ломали разметку Telegram.
- Ошибки Bitrix API (`{"error": ...}` в теле ответа 200 OK) и ошибки Telegram
  API логируются и возвращаются как 502, чтобы это было видно в логах.

## Ручной ввод лидов

Руководитель отправляет номер телефона основному боту в личном сообщении.
Далее бот последовательно предлагает источник, сотрудника отдела продаж и
необязательный комментарий. Лид создаётся после последнего шага и сразу
получает выбранного ответственного. `/cancel` отменяет незавершённый ввод.

Источники загружаются из Bitrix24 и показываются по две кнопки в строке.
`/source` открывает включение и отключение источников. Новые источники CRM
включаются автоматически; отключённые вручную сохраняют состояние.
Сотрудники перечитываются из `SALES_DEPARTMENT_ID` перед показом и повторно
проверяются при выборе.

После создания карточка рассылается руководителям. Привязанный через `/link`
сотрудник получает отдельное уведомление. Кнопка «В мусор» сохраняет лид и
переносит его на стадию «Мусор».

К одному сотруднику Bitrix можно привязать несколько Telegram-аккаунтов. Все
они получают одинаковые менеджерские уведомления о назначенных лидах и сделках,
ручных заявках и ежедневный персональный отчёт. Повторный `/link` с новым
Telegram-аккаунтом добавляет зеркало и не удаляет предыдущую привязку. Такая
привязка не выдаёт административные права или доступ к Mini App.

Постоянное состояние хранится в базе данных и должно входить в резервные копии.
Запускайте один процесс uvicorn: фоновые циклы рассчитаны на один экземпляр
сервиса. Фоновое восстановление
каждые 15 секунд повторяет отправку/обновление карточек после API ошибок.
Если создание CRM лида прервалось с сетевой ошибкой, сервис ищет его по
уникальной метке, вместо повторного создания. Если CRM не создала лид,
карточка остаётся в статусе проверки: администратору нужно проверить CRM
перед отправкой новой заявки. При разрыве соединения после успешной
отправки Telegram, но до сохранения ID сообщения возможна повторная
карточка; сам лид при повторном webhook не создаётся заново.

## Ежедневный отчёт

Каждый день в 19:00 по Москве сервис строит отчёт за событийный интервал от
предыдущих 19:00 до текущих 19:00. Новые обращения учитываются по времени
получения, квалификации — по времени первого выхода из `NEW`, передачи — по
времени смены ответственного после квалификации. Событие ровно в 19:00 входит
уже в следующий отчёт.

Для распределения используется зафиксированный менеджер: пока обращение
находится в `NEW`, это текущий ответственный; после первого выхода из `NEW`
дальнейшие передачи не меняют первоначальную атрибуцию. Результатом
квалификации считается стадия обращения на момент закрытия отчётного интервала,
а не первая стадия после `NEW`.

Продажнику, привязанному через `/link`, приходит личный отчёт: для каждого
источника — одна строка вида `Источник — Лид №1, Лид №2 : «Стадия» (всего: 2)`.
Лиды с одинаковым источником и стадией группируются в одну клаузу (даже если
их ID не идут подряд), чтобы не повторять название стадии на каждый лид.
Каждому руководителю (`DIRECTOR_USERS`) приходит один сводный отчёт со всеми
продажниками подряд, у которых сегодня были лиды — блок начинается с ФИО
сотрудника, дальше тот же формат. Продажники без привязки в `/link` личный
отчёт не получают, но попадают в сводный отчёт руководителя по имени из
Bitrix. Сводка руководителя дополнительно содержит количество лидов и сделок,
распределение новых обращений по источникам, результаты квалификации по
конечным стадиям, обработавших менеджеров, передачи «от кого → кому» и остаток
необработанных на момент отсечки. Если в интервале не было событий, отчёты не
отправляются.

## Интерактивный отчёт в Telegram

Команда `/app` или кнопка «Открыть отчёты» запускает Telegram Mini App. В нём
можно выбрать произвольный период нативным календарём либо одной из быстрых
кнопок. Период определяет когорту обращений по дате их появления: последующие
конверсии и договоры учитываются только для лидов и прямых сделок из этой
когорты.

Перед выдачей результата сервис сверяет текущие стадии лидов и сделок с
Bitrix24. На главном экране показаны конверсии в сделки и договоры, ниже —
раздельные вкладки лидов и сделок. Источники сначала отображаются компактным
списком; по нажатию открывается распределение по стадиям, а нажатие на стадию
показывает ссылки на соответствующие карточки CRM. Для сконвертированного лида
доступны ссылки и на лид, и на созданную из него сделку.

Над вкладками расположен фильтр активных сотрудников отдела продаж из
`SALES_DEPARTMENT_ID`. По умолчанию отдельные переключатели выключены и
отображается общая статистика. Можно включить одного или нескольких менеджеров;
KPI, источники, стадии и количество обращений пересчитываются сразу. Во вкладке
лидов используется текущий ответственный лида, во вкладке сделок — текущий
ответственный сделки. Одинаковый запрос
кэшируется на пять минут, чтобы повторные открытия не создавали лишнюю нагрузку
на Bitrix24.

Построение запускается как фоновая задача, а Mini App короткими запросами
получает текущий этап и процент выполнения. Поэтому доступен диапазон до полного
календарного года, и длительная сверка не обрывается стандартным таймаутом
reverse proxy. Для периодов длиннее 92 дней интерфейс показывает однозначные
названия дат и просит подтвердить запуск. REST-клиент повторно использует
HTTPS-соединения с Bitrix, чтобы не выполнять новое TLS-подключение для каждой
страницы данных.

API отчёта проверяет криптографическую подпись Telegram `initData` и разрешает
доступ только пользователям из `DIRECTOR_USERS` и `ADMIN_USERS`. Обычные
менеджеры, в том числе привязанные через `/link`, доступа к Mini App не получают.
Публичный адрес Mini App задаётся переменной `MINI_APP_URL` (по умолчанию
`https://lead.prav-buro.ru/miniapp`).

Для владельца из `MODE_SWITCH_USER_ID` доступна приватная команда `/mode`.
Она переключает персональную кнопку меню между руководительскими отчётами и
менеджерским «Планом дня». Выбор хранится в основной базе Lead Flow и
восстанавливается после перезапуска. Менеджерский режим использует отдельную
SQLite-базу `MANAGER_PLANNER_DATABASE_PATH`, подписывается токеном текущего бота
и не читает базу прежнего Planner — до завершения миграции оба приложения могут
работать параллельно.

Во время параллельной миграции тот же пользователь может проверить перенесённый
сценарий старого бота командой `/distribution`: выбор до трёх действующих
менеджеров отдела продаж, стадии `IN_PROCESS`/`PROCESSED`/`NEW`, периоды
3–15 дней, замена пустых дат и альтернативные сбалансированные варианты.
Подтверждение повторно сверяет лиды в Bitrix и импортирует задачи менеджерам в
Planner Lead Flow. Пользователи с открытым доступом могут запускать расчёт и
включать напоминание на 10:00 МСК командами `/reminders_on` и
`/reminders_off`; право окончательного подтверждения задаётся отдельно через
`DISTRIBUTION_CONFIRMER_IDS`.

Скрипт `scripts/migrate_legacy_planner.py` делает онлайн-снимки старых Planner,
access/reminders и очереди распределений через read-only SQLite-подключения,
проверяет схемы и `integrity_check`, считает записи и записывает SHA-256 в
манифест. Каждый запуск создаёт новый каталог и не меняет ни источник, ни
предыдущие снимки.

Пока прежний бот остаётся включён, Lead Flow может читать его append-only
очередь распределений через временный мост. Для этого основной Compose запускают
вместе с `docker-compose.legacy-bridge.yml`: каталог очереди монтируется в
контейнер только для чтения, а
`LEGACY_DISTRIBUTION_QUEUE_PATH` указывает на `confirmations.db` внутри mount.
`LEGACY_DISTRIBUTION_CONFIRMER_IDS` задаётся явно и не наследуется из списка
администраторов. Polling идёт с интервалом
`LEGACY_DISTRIBUTION_POLL_SECONDS`; повторно увиденные подтверждения не создают
задач-дублей. После окончательного cutover основной Compose запускается без
override-файла, а пустой путь полностью выключает polling.

### Контроль звонков по сегодняшним лидам и сделкам

Закрытая вкладка «Звонки сегодня» доступна руководителям из `DIRECTOR_USERS`,
администраторам из `ADMIN_USERS` и пользователям из `SUPER_ADMIN_USERS`.
Серверная проверка применяется и к самому API вкладки; скрытие кнопки в
интерфейсе не используется как средство авторизации.

Центральный обработчик МегаФона может пересылать исходный callback на
`POST /megafon/webhook`. Сервис сохраняет только нормализованные поля финального
`history`-события и не сохраняет CRM-токен из payload. Звонок связывается с
лидом или сделкой того же дня по нормализованному телефону. Для сделки телефон
берётся из связанного исходного лида либо основного контакта. Карточка показывает
тип CRM-объекта и его текущую стадию. Если задан `MEGAFON_BITRIX_USER_MAP`,
дополнительно проверяется соответствие внутреннего номера текущему ответственному.

Время реакции считается от последнего события назначения/передачи до первой
исходящей попытки менеджера только внутри рабочего окна 10:00–19:00 МСК.
Например, передача в 18:50 и звонок на следующий день в 10:10 дают 20 минут.

Для состоявшегося звонка раздел показывает первую задачу Bitrix, которую
ответственный менеджер создал или получил по этому лиду/сделке после звонка:
название и срок. Если такой задачи нет, карточка явно сообщает об этом. Аудиозаписи не
скачиваются и не отправляются во внешние сервисы распознавания.

## База данных в production

Docker Compose запускает отдельный PostgreSQL 16 с постоянным volume
`postgres_data`. Перед первым запуском задайте в `.env` длинный буквенно-цифровой
`POSTGRES_PASSWORD`. SQLite остаётся fallback для локальной разработки, когда
`DATABASE_URL` не задан.

Для перехода существующего production-сервиса сначала остановите контейнер
бота и сделайте резервную копию `data/leads.sqlite3`. Затем запустите PostgreSQL
и выполните одноразовый перенос:

```bash
docker compose stop bot-lead-flow
cp data/leads.sqlite3 data/leads.sqlite3.before-postgres
docker compose up -d postgres
docker compose run --rm bot-lead-flow python scripts/migrate_sqlite_to_postgres.py \
  --sqlite /app/data/leads.sqlite3
docker compose up -d bot-lead-flow
```

Мигратор отказывается работать с непустой целевой базой, переносит данные одной
транзакцией и сверяет количество строк во всех таблицах.

## Статистика новых обращений

Сервис хранит минимальный аналитический снимок без контактных данных: тип и ID
объекта, источник, дату создания, текущую стадию и ответственного. Учитываются
все лиды и только сделки основной воронки «Продажа» (`CATEGORY_ID=0`).

Лид или сделка считаются необработанными, пока находятся на стадии `NEW`.
Смена ответственного на этой стадии обновляет текущего владельца. При первом
выходе со стадии `NEW` текущий ответственный навсегда фиксируется как менеджер,
обработавший обращение; дальнейшие передачи эту атрибуцию не меняют.

В `DAILY_STATS_TIME` по часовому поясу `DAILY_STATS_TIMEZONE` бот отправляет
руководителям итог интервала между двумя отчётами: новые обращения,
квалификации с конечной стадией на отсечке, передачи и остаток необработанных.
События после отсечки автоматически попадают в следующий отчёт. Отправка
идемпотентна и восстанавливается после перезапуска приложения.

## Журнал и сверка с Bitrix

Каждый прошедший проверку токена исходящий вебхук сначала записывается в
`bitrix_events`, и только затем обрабатывается. Журнал хранит тип события, ID
объекта, время Bitrix и получения, безопасный payload без токенов, статус,
число попыток и последнюю ошибку. Повторная доставка одного события не
обрабатывается заново, а незавершённые и ошибочные записи повторяются фоновой
задачей до 10 раз.

Дополнительно сервис каждые `RECONCILE_INTERVAL_SECONDS` запрашивает в Bitrix
лиды и сделки направления «Продажа», изменённые после сохранённого курсора.
Окна перекрываются на `RECONCILE_OVERLAP_SECONDS`, поэтому изменение на границе
или временный сетевой сбой не создают разрыв. При первом запуске проверяется
период `RECONCILE_INITIAL_LOOKBACK_HOURS`. Списки Bitrix загружаются со всеми
страницами, а устаревшее состояние не может перезаписать более новое.

## Текущий результат и статистика за период

Раз в сутки в `OUTCOME_SYNC_TIME` сервис перечитывает все сохранённые обращения
из Bitrix и сохраняет человекочитаемое название их текущей стадии. Для
конвертированного лида находится созданная из него сделка направления
«Продажа». Связь определяется прежде всего по `LEAD_ID`, поэтому лид и его
дочерняя сделка не считаются двумя разными обращениями.

Если выигранная сделка продажи скопирована в воронку «Сопровождение»
(`ACCOMPANIMENT_DEAL_CATEGORY_ID=2`), обращение помечается как заключённый
договор. Сначала используется поле «Ссылка на договор»
(`CONTRACT_SOURCE_URL_FIELD`), содержащее ID исходной сделки; затем доступны
резервные сопоставления по уникальному контакту и названию. Факт договора
сохраняется как исторический, а текущая стадия сопровождения обновляется при
следующих сверках.

Руководитель может запросить компактное состояние всех обращений, появившихся
включительно между двумя датами:

```text
/period 01.09.2026 - 23.09.2026
```

Команда каждый раз заново запрашивает в Bitrix лиды, созданные в указанном
диапазоне, их текущие стадии, связанные сделки продаж и договоры в
«Сопровождении». Поэтому результат не зависит от того, был ли объект ранее
получен через webhook. Запрос выполняется в фоне.

В ответ руководитель получает Excel с отдельными листами «Лиды» и «Сделки».
В обоих строки являются источниками, а столбцы — реально встречающимися
стадиями. Конвертированный лид остаётся в таблице лидов в колонке
«Сконвертирован» и одновременно появляется как объект в таблице сделок.
Лист «Итоги» считает обращения без дублей по правилу «лиды + прямые сделки»:
сделка, созданная из уже учтённого лида, второй раз в общий итог не входит.
«Детализация» содержит кликабельные ID лидов, сделок и договоров. В Telegram
остаётся только короткая общая сводка.
