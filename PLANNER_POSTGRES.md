# Planner → PostgreSQL

## Состояние: этапы 1–2 локально, production не переключён

Добавлены реализация PostgreSQL 16 и проверенный локальный мигратор. Перенос production-данных и
переключение production ещё НЕ выполнены. Команды выкладки на этом этапе не нужны.

При пустом `MANAGER_PLANNER_DATABASE_URL` сайт работает с прежней SQLite,
заданной `MANAGER_PLANNER_DATABASE_PATH`. `DATABASE_URL` продолжает выбирать
хранилище ядра бота и не переключает Planner автоматически. При явно заданном
неработающем PostgreSQL URL отката на SQLite не происходит.

В PostgreSQL таблицы сайта находятся в схеме `planner`. Можно использовать ту же
PostgreSQL-инстанцию/базу, но таблицы бота в `public` не смешиваются с таблицами
сайта. Search path не включает `public`. Это разделение пространств имён,
а не замена отдельным ролям и правам: пользователь с правами владельца БД
по-прежнему может обращаться к другим схемам явно. Выбор production-ролей
и выдача прав входят в подготовку переключения.

## Что реализовано

- Общие бизнес-операции Store и отдельный PostgresStore, без копирования бизнес-правил.
- Явные операции выдачи ID (`RETURNING id`), версии схемы и выбора рабочего дня.
- Схема v8: связи сотрудников, планы, задачи, переносы, согласования, отчёты,
  аудит, distribution inbox, журнал попыток и история legacy-импорта.
- BIGINT для ID (включая Telegram ID больше 2^31) и секунд; DOUBLE PRECISION
  для вещественных показателей; JSON-снимки пока остаются TEXT для точного
  сохранения исходного содержимого.
- Отдельный маркер приложения/версии и отказ от неизвестной, неполной или
  более новой схемы. Повторный запуск не пересоздаёт сотрудников и привязки.
- Транзакции записи READ COMMITTED с одной advisory transaction lock перед
  чтением бизнес-состояния. Это сохраняет последовательность проверок и записи,
  которую обеспечивал SQLite BEGIN IMMEDIATE. Пока записи одного Planner
  сериализуются; увеличение параллелизма требует отдельного пересмотра блокировок.
- Транзакции чтения REPEATABLE READ READ ONLY: согласованный снимок и запрет записи.
- Ограничения времени соединения, ожидания блокировок и SQL-запроса.
- Триггеры неизменяемости reports/audit/system_audit для UPDATE, DELETE и TRUNCATE.
- Обработка ошибок обоих драйверов в API и legacy-bridge; конфликты → 409,
  недоступность хранилища → 503, без раскрытия деталей подключения.

## Локальные проверки

`tests/test_planner_postgres.py` запускает PostgreSQL-тесты только при явно заданном
`PLANNER_TEST_DATABASE_URL`. Он ПЕРЕСОЗДАЁТ схему planner и допускает только
одноразовую базу `planner_test` на localhost/127.0.0.1/planner-postgres-test.
Не указывать production-реквизиты. Для SQLite-регрессии переменная не нужна.

Выполнен полный набор unittest в Python 3.12 и PostgreSQL 16, в изолированных
локальных Docker-контейнерах, без публикации портов и боевых данных. Новые проверки:
выбор хранилища; большие ID и aliases; повторный startup; совпадение колонок
SQLite/PostgreSQL; жизненный цикл плана/согласования/таймера/отчёта; копирование
рабочего дня; перенос задач; откат транзакции; FK/unique; запрет записи при чтении;
изоляция search path; согласованный снимок; неизменяемость отчётов/аудита;
одновременные правки, запуск таймеров и импорт; legacy bridge; ошибки API и
конфигурация API; отказ от чужой/неподдерживаемой схемы.

Контрольная запись в public проверяется после каждого PostgreSQL-сценария:
работа Planner не меняет данные другой схемы.

## Этап 2: перенос и независимая сверка

Новый инструмент — `scripts/migrate_planner_to_postgres.py`. Это мигратор
**Planner**, старый `scripts/migrate_sqlite_to_postgres.py` относится к боту.

По умолчанию выполняется только анализ указанного SQLite-снимка: PostgreSQL
не подключается даже при наличии URL в окружении. Источник открыт `mode=ro`,
`query_only=ON`, с одной read-транзакцией для проверки и копирования.
Проверяются версия v8, структура всех 14 таблиц, integrity/FK, представимость
значений в PostgreSQL и SHA-256 содержимого каждой таблицы. Посторонние таблицы
или неподдерживаемая структура не игнорируются: инструмент отказывается от переноса.

Пример **локального** анализа согласованного тестового снимка:

```bash
python scripts/migrate_planner_to_postgres.py --source /tmp/planner-snapshot.sqlite3
```

Результат содержит `source_data_sha256` — отпечаток данных выбранной read-транзакции,
а не хеш основного файла SQLite (он может иметь WAL). Отчёт не содержит строк
таблиц, паролей или URL подключения.

Для `--check-target`, `--apply` или `--verify` URL задаётся явно в отдельной
переменной `PLANNER_MIGRATION_DATABASE_URL`. `DATABASE_URL` и runtime
`MANAGER_PLANNER_DATABASE_URL` мигратор не подхватывает. Это не меняет конфигурацию
работающего сайта. Не передавать пароль аргументом командной строки.

Режимы:

- Без флагов: только источник, без подключения PostgreSQL.
- `--check-target`: дополнительно read-only проверка пустоты схемы planner.
- `--apply --expected-source-sha256 <отпечаток>`: явный перенос проверенного
  набора данных в отсутствующую или пустую схему. Отпечаток берётся из dry-run;
  изменение даже одной строки с тем же количеством записей потребует новой проверки.
- `--verify`: независимая read-only сверка уже перенесённой/восстановленной БД
  с указанным снимком. Последовательности ID не расходуются.

В apply перед записью берётся та же транзакционная advisory lock, что у Store,
и заново проверяется пустота схемы. Даже таблицы без строк, функции, типы,
последовательности или уже инициализированный сайт блокируют перенос. Нет DROP,
TRUNCATE, очистки существующих таблиц, автоматического merge или переименования ID.

DDL, COPY, восстановление связей задач, сверка содержимого и RESTART identity
выполняются в одной PostgreSQL-транзакции. Задачи копируются сначала без
moved_to/source_task_id, затем ссылки восстанавливаются после появления всех ID,
с включёнными FK. Отчёты, аудит, JSON-строки, aliases, роли, таймеры, timestamps,
legacy_imports и история schema_migrations копируются без нового seed.
Новые ID начинаются после максимального перенесённого ID; для пустых таблиц — с 1.

Сверяются и количество, и SHA-256 строк всех таблиц. Текстовые ключи сортируются
в SQLite BINARY/PostgreSQL C, чтобы локаль PostgreSQL не меняла порядок хеширования.
При сбое COPY, сверки или RESTART вся новая схема/данные откатываются.
Ранее существовавшая пустая схема при этом сохраняется пустой. Повторное применение
к готовой схеме отказывается работать и не затрагивает новые данные.

Перенесённый `timer_started` сохраняется без поправок: работающий таймер продолжит
учитывать прошедшее время. Перед production-переносом нужно отдельно решить,
следует ли сотрудникам остановить таймеры. Мигратор сам их не останавливает.

Проверки: синтетические данные во всех 14 таблицах, закрытые отчёты и аудит,
дробные показатели, Unicode/переводы строк, forward/backward ссылки задач,
AndreyK с ролью supervisor, большие ID, активный таймер, пустые таблицы,
обновление identity и параллельный запуск двух миграторов. Проверены отсутствие
изменений SQLite и public, отказы при повреждении источника/изменении отпечатка,
непредставимых значениях и непустой цели; внедрены сбои после частичного COPY,
во время сверки и после RESTART для проверки полного rollback.

## Следующие этапы до production

1. Подготовить production-права и backups. Текущий deploy/backup-bot-lead-flow
   сохраняет Planner SQLite; не считать его готовым к PostgreSQL-переключению.
2. Репетиция на копии данных: backup → перенос → запуск → запись новых сущностей
   → восстановление PostgreSQL backup. Старые SQLite-импортёры не должны служить
   способом записи в активную PostgreSQL. Production-снимок пока не запрашивался
   и не использовался: все проверки выполнены на вымышленных данных.
3. Пользователь выполняет production-переключение с короткой остановкой записи,
   последним снимком и планом отката. Сразу после новых записей в PostgreSQL
   старый SQLite уже отстаёт: простой возврат переменной назад потеряет эти
   изменения, поэтому откат после возобновления записи требует отдельного решения.

Мигратор не переключает runtime и не настраивает двойную запись.
Автоматического переноса при запуске сайта нет.
