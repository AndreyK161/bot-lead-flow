# Архитектура Lead Flow

## Два сервиса в одном репозитории

| Сервис Compose | Контейнер | Entry point | Ответственность |
| --- | --- | --- | --- |
| `bot-lead-flow` | `leadflow-bot` | `apps.bot.backend.main:app` | Telegram, Bitrix/МегаФон webhook, бот-отчёты, сверка CRM, рассылки и фоновые задачи |
| `planner` | `leadflow-planner` | `apps.planner.backend.main:app` | Сайт «План дня», `/manager/api/`, планы, задачи, таймеры, согласования и импорт подтверждений |
| `postgres` | прежнее имя Compose | PostgreSQL 16 | Основная база и надёжная очередь между приложениями |

Сервисы не зависят друг от друга в Compose. Они зависят от PostgreSQL.
Остановка бота не останавливает сайт; остановка сайта не останавливает webhook
и фоновые циклы бота. Оба приложения по-прежнему зависят от общей БД и внешних
Bitrix/Telegram/телефонии для соответствующих функций.

## Код

```text
apps/
  bot/backend/       # бот, webhook, CRM, телефония, реестр допуска
    static/          # старый Telegram-интерфейс отчётов бота
  planner/
    backend/         # API, бизнес-правила и отдельный lifespan сайта
    frontend/        # React + TypeScript + Vite
    static/          # собранный сайт
  shared/            # контракт распределения и доступ к надёжной очереди
```

Сайт работает в браузере и через Telegram; копии frontend нет.
В бот не монтируется `/manager/`. Сайт не обслуживает `/telegram/webhook`,
`/bitrix/webhook` или `/megafon/webhook` и не запускает polling/рассылки бота.

Сайт использует библиотечные модули настроек, реестра доступа, Bitrix-клиента и
обзвона из `apps/bot/backend/`. Интерфейс отчётов бота использует CRM-адаптер
Planner. Это Python-библиотеки, не обращения к процессу другого сервиса.
Ни один entry point не импортирует и не запускает entry point второго.
Docker-образы пока содержат общий Python-код для этих зависимостей; выделение
отдельных пакетов общего кода можно сделать позже без объединения процессов.

## Доставка распределений при остановленном сайте

1. Бот проверяет право подтверждения и сохраняет сообщение schema=1 в
   `planner_distribution_outbox` основной БД. В production это PostgreSQL.
2. Сообщение содержит ID подтверждения, рабочую дату, исходный JSON и SHA-256.
   Повторное подтверждение не создаёт второе сообщение; бизнес-поля должны совпадать.
3. Только сайт читает pending-сообщения, проверяет контракт и импортирует их в
   свою базу. Доставка по умолчанию проверяется каждые 5 секунд.
4. После успешной локальной транзакции сайт подтверждает `imported` либо `review`.
   При сбое между коммитом и подтверждением повторный импорт идемпотентен.
5. Ошибки оставляют запись pending с attempts/last_error для повторной обработки.
   Если сайт недоступен, бот честно сообщает о сохранении, а не о готовых задачах.

Бот не открывает SQLite Planner и не нуждается в томе его данных. Изменённый
снимок для уже подтверждённого рабочего дня не перезаписывает исходный.
Закрытые отчёты сохраняются: распределение для закрытого плана уходит в review.

Старая внешняя SQLite-очередь остаётся только мостом совместимости. Если он нужен,
`docker-compose.legacy-bridge.yml` подключается к сервису `planner`; только сайт
запускает её потребитель. Общий контракт вынесен в `apps/shared/distributions.py`.

## Хранилища и границы этапа

- `DATABASE_URL` у обоих сервисов указывает на существующую PostgreSQL бота.
- Planner пока хранит основные данные в SQLite по
  `MANAGER_PLANNER_DATABASE_PATH` (`data/manager_planner.sqlite3` по умолчанию).
- Прежний `./data:/app/data` подключён к сайту, путь и содержимое БД не менялись.
- Основная база, Compose project name и том `postgres_data` не переименовывались.
- Инициализация общей PostgreSQL сериализована транзакционной advisory-блокировкой,
  чтобы одновременный запуск двух процессов не запускал DDL параллельно.
- SQLite fallback основной БД сохранён для локальных unit-тестов. Compose явно
  использует PostgreSQL; новая SQLite-очередь для живых подтверждений не вводится.

Миграция основных данных Planner в PostgreSQL — отдельная задача.

## Сборка и независимые обновления

Dockerfile имеет targets `bot` и `planner` с разными CMD. По умолчанию последний
stage — бот. Compose использует targets явно. Образы имеют разные имена:
`bot-lead-flow-bot:latest` и `bot-lead-flow-planner:latest`. Для раздельных версий
можно задать `BOT_IMAGE` и `PLANNER_IMAGE`.

После первоначального перехода и при работающей PostgreSQL:

```sh
# Пересобрать и обновить только сайт:
docker compose up -d --build --no-deps planner
# Пересобрать и обновить только бота:
docker compose up -d --build --no-deps bot-lead-flow
# Перезапустить без пересборки:
docker compose restart planner
docker compose restart bot-lead-flow
```

Не использовать `--workers` больше 1 для любого из сервисов: бот имеет фоновые
циклы, сайт — потребителя распределений и локальное SQLite-хранилище.
Обновление общей схемы/контракта требует совместимости обоих образов; отдельные
контейнеры не отменяют эту проверку при будущих миграциях БД.

Для локального `npm run dev` Vite проксирует `/manager/api` на отдельный
сайт `http://127.0.0.1:8082`, а не на процесс бота.

Frontend собирается до Python-образа:

```sh
cd apps/planner/frontend
npm ci
npm run build
npm run test:api
npm run test:ui
npm run test:navigation
npm run test:profile
npm run test:login
```

Vite выводит файлы в `../static/` с base `/manager/`. Python Dockerfile не
запускает Node/Vite. Браузерным тестам нужен Chromium Playwright, при необходимости
путь задаётся через `PLAYWRIGHT_CHROMIUM_EXECUTABLE_PATH`.

## Первая выкладка после разделения

Это отдельная согласованная операция, здесь она не выполнялась.

- Проверить свободный порт сайта. В шаблонах это `127.0.0.1:8082`, переменные
  `PLANNER_BIND`/`PLANNER_PORT`. Бот сохраняет `APP_BIND`/`APP_PORT`.
- В первый раз нужно создать сервис `planner` и обновить бота, а не только
  перезапустить прежний общий контейнер. Обычный restart новую структуру не применит.
- Все Nginx location `/manager/` и `/workday/` должны вести на порт сайта;
  webhook и бот-отчёты остаются на порту бота. Шаблоны в `deploy/` обновлены.
- `flow.prav-buro.ru` отправляет `/health` на сайт. У обоих сервисов собственный
  `/health`; у Planner также сохраняется `/manager/healthz`.
- Если используется старый мост распределений, перенести override на `planner`.
- Обновить установленную копию `backup-bot-lead-flow`: PostgreSQL и outbox входят
  в pg_dump, SQLite снимается с `leadflow-planner`. Источник открывается read-only,
  чтобы ошибочное имя контейнера/путь не создали пустую базу.
- Systemd-шаблоны разделены: прежний bot-lead-flow и новый leadflow-planner.
  На сервере их установка автоматически не производится.

Не удалять `data/`, том PostgreSQL или прежние резервные копии. Возможность
возврата к старому общему образу нужно проверять по очереди pending: старый код
не умеет читать новый outbox. Одного возврата старого образа недостаточно для
обработки подтверждений, накопленных после перехода.

## Проверки

Из корня: `python3 -m unittest discover -s tests -q`.
Тесты проверяют владение маршрутами, раздельные lifecycle, отсутствие фоновых
задач бота у сайта, доставку после остановки потребителя, идемпотентность,
конфликты и сохранность закрытых отчётов. Внешние вызовы в unit-тестах замоканы.
